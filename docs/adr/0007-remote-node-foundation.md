# 0007. Remote Node identity, trust, and autonomous-node boundary

## Problem

GameNode v0.5 introduces the idea of a controller that can observe multiple GameNode installations ("nodes"). Before any remote server management can exist, GameNode needs a durable identity for each node, a way for an operator to deliberately enroll one node into another as a controller, and a trust/authentication model for that relationship - all without turning a single autonomous, self-contained node into a component that depends on, or can be taken over by, a controller.

## Options considered

1. **Hostname or IP as node identity.** Rejected: both change (DHCP, renaming, NAT, container restarts) and neither is under GameNode's control; identity must survive all of that.
2. **Shared/replicated SQLite between controller and node**, or the controller opening a remote node's database directly (e.g. over a mounted volume or a DB-level protocol). Rejected outright: it would make the "node" a dumb worker instead of an autonomous installation, contradicting the product's single-node-first design (see `AGENTS.md` and `PROJECT_PLAN.md`'s Vision).
3. **Reuse the existing browser cookie session (and its CSRF token) as the machine-to-machine credential** for controller→node calls. Rejected: cookie sessions are a human trust domain (`internal/auth`) with a 24h lifetime, same-origin/CSRF semantics that do not apply to a server-to-server caller, and no concept of "this is a controller, not a person". Reusing it would blur an already-reviewed security boundary.
4. **Full mTLS with a certificate authority and lifecycle GameNode manages.** Attractive long-term, but the repository has no certificate issuance/rotation/revocation infrastructure today, and building one is a large, separately-reviewable milestone of its own. Deferred; see Decision below for how this stays reachable later without a redesign.
5. **A dedicated pairing/enrollment flow that issues a bearer machine credential, structurally separate from human sessions, plus a small typed Node API and a narrow outbound client.** Chosen.

## Decision

- **Node identity (`internal/nodeidentity`)** is a random, high-entropy `NodeID` generated exactly once and persisted in the node's own SQLite (`node_identity`, migration `023_remote_nodes.sql`). It never derives from hostname, IP, MAC address, or the database path, so renaming the machine or moving the database file cannot change it. A separate, optional, operator-set `display_name` is metadata only.
- **Protocol version** is a small integer (`nodeidentity.ProtocolVersion`, currently `1`), independent of the GameNode product/release version string. A controller compares this integer, never a version string, to reason about compatibility.
- **Capabilities** are a fixed, reviewed list of typed string identifiers (`nodeidentity.Capabilities()`) describing what this build genuinely implements - never derived from reflecting over internal Go service types, and never advertising a feature (such as v0.4's Egg Runtime) that is not actually present on the running branch.
- **Trust is established only through deliberate pairing**, never by IP, hostname, or first contact:
  - An operator on the *target* node generates a single-use, time-bounded (15 minute) pairing token (`POST /api/v1/node/pairing-tokens`, human session + `Node.Manage` + CSRF). Only its salted SHA-256 hash is stored (`node_pairing_tokens`); the plaintext is returned exactly once and is never logged or placed in audit metadata.
  - An operator on the *controller* side supplies that token and the node's endpoint to `POST /api/v1/remote-nodes` (human session + `Node.Manage` + CSRF). The controller's `internal/remote.Client.Enroll` calls the node's `POST /api/v1/node/enroll` with the token and nothing else - no prior Authorization header.
  - The node validates and atomically consumes the token (replay-proof: a second use fails exactly like an unknown or expired one, to avoid leaking which case occurred), then issues a new high-entropy **machine credential**, storing only its hash (`node_trusted_callers`) and returning the plaintext exactly once.
  - The controller persists that credential in its own `remote_nodes` registry row and presents it as `Authorization: Bearer <credential>` on every subsequent call. It is never re-displayed through any controller-facing API response.
- **Human and machine trust are structurally separate** (`internal/api`'s `requireAuth`/CSRF path vs. `requireMachineAuth`): the Node-facing API (`/api/v1/node/info`, `/health`, `/capabilities`) accepts only a valid `Authorization: Bearer` machine credential and performs no same-origin/CSRF check (those are human-browser concepts); the controller-facing registry API (`/api/v1/remote-nodes*`, pairing token issuance) accepts only a human session and enforces RBAC (`Node.View`/`Node.Manage`) and CSRF exactly like every other mutation in the product.
- **The remote client boundary is narrow and typed** (`internal/remote.Client`): `Enroll`, `GetNodeInfo`, `GetHealth`, `GetCapabilities` - no `DoRequest(method, arbitraryURL, body)` escape hatch reaches product layers. Every call has a bounded timeout (8s default), a bounded response body (1 MiB), real TLS certificate verification (no `InsecureSkipVerify`), and stops at the first response instead of following a redirect - a Remote Node redirecting to a different origin would otherwise be an SSRF/credential-leak primitive, since Go's default client would replay the `Authorization` header there.
- **Endpoints are validated and normalized** to bare `scheme://host[:port]` (`remote.ValidateEndpoint`): no path, query, fragment, or userinfo survives, and only `http`/`https` are accepted. GameNode does not restrict endpoints to public addresses: operators intentionally point this at loopback, private-network, or public hosts, so the SSRF mitigation is "only ever call the one enrolled endpoint with fixed typed paths and a bounded response", not an IP allowlist.
- **Health is a small classified enum** (`nodes.Health`: `reachable`, `unreachable`, `authentication_failed`, `protocol_incompatible`, `degraded`, `unknown`), never a raw Go network/TLS error. A bounded, periodic background refresh (`internal/api.Server.StartHeartbeat`, 30s interval, 5s per-node timeout, cancelled cleanly on shutdown) updates it; one unreachable node never blocks or delays another, and a failed refresh preserves the last-known-good metadata and `last_seen_at` rather than zeroing it.
- **Connection state is presentation only.** A remote node's registry entry (`internal/nodes`) never becomes authoritative over that node's own server/runtime lifecycle: "unreachable" is shown as exactly that, never translated into "servers stopped," and disabling or deleting a registry entry never contacts the remote node or affects its workloads.
- **This node's own autonomy is unconditional.** Enrollment (in either direction) never introduces a dependency: local UI, API, RBAC, `servers.Service`, runtimes, Console, Filesystem, and monitoring keep working exactly as before, whether or not any controller relationship exists or is currently reachable.

## Trade-offs

Pairing-token enrollment plus a bearer machine credential is materially simpler to ship correctly in this milestone than full mTLS, at the cost of a credential that (unlike a client certificate) is a bearer secret: possession alone authenticates, so its storage, redaction, and non-forwarding-across-hosts properties matter, all of which this decision assigns to `internal/nodes` (hash-only storage) and `internal/remote` (never resent to another host, never logged). The pairing token's short lifetime and single-use consumption bound the exposure of the one moment where trust is bootstrapped from nothing. The design deliberately keeps the machine-credential concept (`nodes.TrustedCaller`, `remote_nodes.credential`) narrow enough that a future milestone can add mTLS as an additional or replacement transport-level credential without redesigning the Node/pairing model - the enrollment handshake would simply also exchange or verify a certificate.

## Consequences

- `internal/nodeidentity`, `internal/nodes`, and `internal/remote` are new, transport-adjacent-but-independent packages; `internal/api` gains machine-authenticated Node-facing routes and human-authenticated, RBAC/CSRF-protected controller-facing routes, following the same patterns as `internal/tenants`/`internal/api/tenants.go`.
- Any future v0.5B remote server management must reuse this same trust boundary (typed `remote.Client` methods, machine credential, RBAC-gated registry mutation) rather than inventing a second one; it must not let controller connectivity become authoritative over a remote server's lifecycle.
- A future mTLS milestone can extend enrollment to also bind a certificate, but does not need to replace the pairing-token bootstrap or the registry schema.
- Remote Server mutation, remote console/files, provisioning, scheduling, and cluster state remain explicitly out of scope for this decision; see `PROJECT_PLAN.md`'s v0.5B/v0.5C/v0.6 milestones.
