# 0010. Container placement execution over the existing provisioning path (v0.6)

## Problem

`docs/adr/0009-cluster-scheduling-decision-vs-execution.md` deliberately stopped v0.6's first phase at a placement DECISION: `POST /api/v1/cluster/placement` never creates, starts, or mutates anything, and a Remote Node target was always `requires_v0.5b` - a proposal only, because there was no way to create a server on a Remote Node at all. The remaining task is to let a caller actually act on a `container` (and `native`) placement decision without reopening any of the boundaries ADR 0009 drew: no full v0.5B remote server management, no second container-lifecycle implementation, no direct Docker access from placement or the controller, no failover/migration/controller election/reservations.

## Options considered

1. **Give `internal/placement` (or the controller) a Docker client / call `internal/runtime` directly.** Rejected outright: this recreates a second container-lifecycle implementation next to `internal/runtime`/`internal/provisioning`, bypasses every validation `provisioning.Service` already performs (template/Egg compatibility, the image allowlist, resource limits, the tenant/filesystem sandbox), and puts Docker access somewhere other than the one reviewed place it belongs. Forbidden by `AGENTS.md` §4 and by this milestone's own constraints.
2. **Build a generic remote server-create endpoint (`POST /api/v1/remote-nodes/{id}/servers` taking a raw `servers.Server`-shaped payload) and let placement call that.** Rejected: a bare `servers.Server` payload has no place for container/Egg-specific data (image, resource limits, installer plan) without either omitting container placement entirely or inventing a second, parallel container payload shape next to `provisioning.Request`. It would also either skip template/Egg/image/resource validation (unsafe) or duplicate it outside `provisioning.Service` (a second implementation) - both rejected by option 1's reasoning. It is also most of v0.5B's scope (general remote server management), which stays out of scope here.
3. **Add one narrow, typed remote provisioning path that mirrors the existing local provisioning API exactly, and dispatch through it.** A new machine-authenticated `POST /api/v1/node/provisioning` on the target node accepts the same bounded fields the existing browser-facing `POST /api/v1/templates/{id}/provision` already accepts (see `internal/api/provisioning.go`'s `provisionInput`), and forwards straight into that node's own, unmodified `provisioning.Service.Start`. A controller-side proxy, `POST /api/v1/remote-nodes/{id}/provisioning`, only authenticates, checks RBAC/CSRF/tenant scope, and forwards. `POST /api/v1/cluster/placement/execute` recomputes the decision server-side and dispatches to either the local `provisioning.Service` (selected node is this installation) or the remote proxy call (selected node is a Remote Node) - never anything else. Chosen.

## Decision

- **`internal/placement` does not change its shape.** `Decide` still takes an already-built candidate list and returns a `Decision` with zero I/O. The only change inside the package is renaming `ExecutionRequiresV05B` (`"requires_v0.5b"`) to `ExecutionRemoteProvisioning` (`"remote_provisioning"`), because a Remote Node target genuinely can be acted on now - through this one narrow path, not general v0.5B remote server management. `internal/placement` still imports nothing from `internal/runtime`, `internal/provisioning`, or `internal/remote` (enforced by a static source-scan test, `TestPlacementPackageNeverImportsRuntimeOrDocker`).
- **`POST /api/v1/cluster/placement` keeps its exact ADR 0009 behavior**: decision only, never mutates anything, audited once per request under `cluster.placement_decide`.
- **`POST /api/v1/cluster/placement/execute` is a new, separate, explicitly-named endpoint.** It: (1) decodes the same typed provisioning fields the local provisioning route already accepts; (2) authorizes tenant-scoped `Cluster.Schedule` + `Server.Create` + global `Templates.View` (CSRF required); (3) computes the placement decision itself, server-side - a caller can never pass in or influence a prior decision; (4) stops and audits a rejection without dispatching anything; (5) for a `local_only` decision, calls `provisioning.Service.Start` directly - the exact same call the existing browser-facing provisioning route makes; (6) for a `remote_provisioning` decision, calls the new remote dispatch path. Exactly one `cluster.placement_execute` audit event is recorded per request, success only when a node was selected AND the target accepted the provisioning request.
- **The remote path is exactly two new routes, both narrowly typed:**
  - `POST /api/v1/node/provisioning` (+ `GET`/`POST .../{jobID}[/cancel]`) - machine-authenticated (the same `Authorization: Bearer <credential>` trust domain as every other `/api/v1/node/*` route, completely separate from browser cookie/CSRF trust - see `docs/adr/0007-remote-node-foundation.md`). It forwards straight into `provisioning.Service.Start`/`Get`/`Cancel` on the node that receives the call. That node remains the sole authority for template/Egg validation, the image allowlist, resource limits, its tenant/filesystem sandbox, the container installer, job persistence, and final registration through `servers.Service` - nothing about `provisioning.Service`'s validation is skipped, weakened, or reimplemented for a remote-originated request. Jobs created this way carry a fixed synthetic actor identity (`"remote-controller"`) instead of a local user account, since Remote Node machine-auth carries no per-caller user identity (see `internal/nodes/pairing.go`).
  - `POST /api/v1/remote-nodes/{id}/provisioning` (+ `GET`/`POST .../{jobID}[/cancel]`) - the ordinary browser-authenticated, RBAC- and CSRF-protected controller-side proxy. It authenticates, checks RBAC/CSRF/tenant scope, looks up the target's stored endpoint/credential (`nodes.Service.Credential`), forwards the typed request through `internal/remote.Client.StartProvisioning`/`GetProvisioningJob`/`CancelProvisioningJob`, and returns the bounded job the target reports - `provisioning.Job`, unmodified. It never interprets container/Egg data itself, never talks to the target's database, and never calls Docker. A rejected remote provisioning request (invalid image, resource limits, non-provisionable template, …) surfaces through a new `*remote.ProvisioningError` type that carries the target's own typed error code/message straight through, instead of collapsing every 4xx into one generic transport error - a rejected remote container placement is exactly as diagnosable as a rejected local one.
  - Neither route accepts anything beyond the fields `provisioning.Request` already has: no raw JSON, no generic map of engine flags, no mounts/devices/capabilities/host networking/registry credentials/installer scripts. There is no way, through either route, to reach a container capability the local provisioning API could not already reach.
  - The controller keeps **no new persistent job/tenant mapping**. A job-status/cancel read against `/api/v1/remote-nodes/{id}/provisioning/{jobID}` requires a `tenant_id` and trusts only the *target node's own* `tenant_id` field on the returned job, refusing (`404`) a mismatch - this avoids inventing a cluster-wide reservation/index table while still enforcing tenant isolation on every read.
- **Native placement is unchanged.** `runtime_type=native` placement execution still ends up as an ordinary `provisioning.Service.Start` call (local) or the same remote provisioning dispatch (remote) - there is no separate "native execution" code path, and nothing about the existing native create flow is modified.
- **No native fallback for a failed container placement.** If container provisioning fails - synchronously (invalid image, non-provisionable template) or asynchronously (installer/resource-limit failure inside the job) - the job fails and stays failed. `/execute` never retries the same request as `runtime_type=native`, and no other code path does either.

## Trade-offs

This still does not deliver v0.5B: there is no way to start, stop, restart, update, or delete an *already-existing* server on a Remote Node, and no read of a remote node's server inventory beyond what v0.5A's health/capability calls already expose. A future v0.5B can add that without redesigning any of this: `internal/remote.Client` already demonstrates the pattern (typed request struct, machine-authenticated node-side handler, typed response, sanitized error mapping) a general remote server-management API would reuse, and `placement.Decide`/`ExecutionRemoteProvisioning` would not need to change. Capacity, migration, failover, controller election, and cluster-wide reservations remain exactly as out of scope as ADR 0009 already decided - nothing in this addendum assumes a server can move between nodes, and the existing local provisioning target-directory conflict protection is reused unchanged, not duplicated into a new cluster-wide reservation mechanism.

## Consequences

- `internal/placement`'s public contract changes by exactly one renamed constant (`ExecutionRemoteProvisioning` replacing `ExecutionRequiresV05B`); `Decide`'s algorithm, inputs, and every other exported symbol are unchanged.
- `internal/remote.Client` gains three new typed methods (`StartProvisioning`, `GetProvisioningJob`, `CancelProvisioningJob`) and one new typed error (`ProvisioningError`), following the same fixed-path, bounded-timeout, bounded-response-size, no-redirect-following discipline the rest of the client already uses.
- `internal/api` gains two new route families (`/api/v1/node/provisioning...`, `/api/v1/remote-nodes/{id}/provisioning...`) and one new handler (`/api/v1/cluster/placement/execute`), all reusing existing RBAC permissions, the existing CSRF/machine-auth trust domains, and the existing `provisioning.Service`/`servers.Service` - no new service package, no new job-tracking mechanism, no new migration.
