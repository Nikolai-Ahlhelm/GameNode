# Security

- Passwords are hashed with Argon2id; plaintext passwords are neither logged nor persisted.
- Local-user creation and password resets reuse the same Argon2id implementation and require passwords of 12–256 characters. There are no composition rules and neither API responses nor logs include password hashes.
- Disabling or deleting a user removes all of that user's sessions immediately; password resets also revoke existing sessions. Disabled and deleted users therefore cannot establish or retain authenticated sessions.
- The last enabled administrator cannot be disabled, deleted, or demoted. Management APIs use global RBAC permissions and normal CSRF protection. `Users.Manage` does not delegate administrator-flag changes; those remain active-admin-only. Login failures remain generic.
- User and group names are restricted to ASCII identifiers and stored under SQLite's case-insensitive uniqueness semantics, avoiding silent Unicode normalization ambiguity.
- RBAC permission keys are selected only from a compiled static catalog; roles and group names have no implicit privilege. The evaluator is allow-only, supports global/tenant/server scopes, and denies disabled users before the administrator bypass or assignments. Enabled administrators retain the bypass. Server, Console, Files, and existing Users/Groups/Roles management endpoints consume this evaluator. Platform permissions - including the new `Tenants.View`/`Tenants.Manage`, which administer tenant entities themselves - are checked only at global scope, so a tenant- or server-scoped role cannot expose management data. There is no implicit permission inheritance: `Manage` never implies `View`, and a tenant/global grant reaching a server never implies rights on a sibling server outside that grant's own scope.
- A permission evaluated against a specific server also automatically checks that server's own tenant: it is effective via an enabled admin bypass, a global assignment, a tenant assignment for that server's tenant, or a server assignment for that exact server - never a tenant assignment for a *different* tenant, even one holding a sibling server. Tenant membership (`internal/tenants`) by itself never grants a permission; only a role assignment does. `Server.Create` is the one permission that is global- or tenant-scoped but never server-scoped, since it is evaluated before any server exists.
- Every server-ID-based API route (detail, edit, delete, lifecycle, console WebSocket, files, configuration, ports, monitoring) authorizes through this same evaluator with no separate tenant check; a denied cross-tenant request always returns a uniform `403 Forbidden`, never a different status that would distinguish "wrong tenant" from "does not exist". The dashboard and `GET /servers` filter purely by calling the evaluator per server before aggregating, so a Tenant B server's existence, name, or count is never inferable from a Tenant A user's dashboard totals. `internal/api/cross_tenant_test.go` regression-tests both properties end to end with two fully independent tenants.
- `Server.Create`'s tenant scope is honored only by managed template/SteamCMD provisioning (`POST /templates/{id}/provision`), whose request body carries a `tenant_id` and a relative `directory_name` but no host-path field at all. `POST /servers` (Custom Application, Adopt Existing) and `POST /templates/{id}/adopt` (NeoForge adopt) both accept an arbitrary admin-supplied host path and therefore deliberately require *global* `Server.Create` only, so a tenant-scoped grant can never register or point a server at an arbitrary filesystem location.
- **Tenant boundaries are an API/application access-control boundary, not a hostile-process sandbox.** A tenant boundary determines which authenticated users may reach a server's records, files, console, ports, and monitoring through GameNode's own API; it says nothing about the server's own native OS process. Every server GameNode manages - regardless of tenant - is a plain OS process launched under the same account and privileges as the GameNode service itself. Tenants do not get separate OS user accounts, containers, namespaces, cgroups, or any other kernel-level isolation, and none is planned for this milestone. A game process that is compromised (a malicious mod, a vulnerable server binary, a poisoned world save) runs with GameNode's own OS service-context rights and can, at the OS level, affect the host and every other process the service account can reach - including servers belonging to other tenants - regardless of which tenant "owns" it in GameNode's database. Do not present GameNode's tenants as secure multi-tenant hosting for mutually distrusting or adversarial operators; they exist to organize and scope *access*, not to contain a hostile workload. Operators who need real workload isolation between tenants must provide it themselves (separate OS accounts/VMs/containers per tenant, run on separate hosts, or an equivalent external boundary) - GameNode does not.
- The Tenant administration UI (`web/src/tenants.tsx`) is purely a client of the same evaluator: it renders `EmptyState`/hides Create actions when the actor lacks the relevant permission but performs no authorization decisions of its own, and every list it shows (a tenant's servers, its members, its access assignments) is populated by calling an already-scoped backend endpoint - `GET /servers` filtered client-side to the tenant for the Servers tab (so it can never show a server the actor could not otherwise see through the ordinary server list), and `GET /tenants/{id}/members`/`GET /tenants/{id}/access` under their own `Tenants.View`/`Roles.View` gates for the other tabs.
- Monitoring reads require `Monitoring.View` at the requested server scope. Sampling verifies full process identity before collecting metrics and discards stale samples, so a reused PID is not attributed to a newer process. Sampling errors only degrade health and never interrupt lifecycle or console handling.
- Auto-restart attempts are bounded in a rolling window. Pending generations are cancelled by manual lifecycle intent, and a replacement process receives a fresh identity and console session.
- Audit metadata is server-controlled valid JSON capped at 4096 bytes; it is never automatically copied from request bodies. Audit events never store passwords, hashes, sessions, CSRF tokens, cookies, Authorization headers, console stdin, file contents, or upload contents. The product API exposes no audit PATCH/DELETE. SQLite administrators can still alter the database directly; v0.1 provides neither signatures, hash chains, nor cryptographic tamper evidence. Audit writes are best effort: a persistence error is logged but does not reverse a completed product operation.
- 6D.2a audits normal credential-login success and failure and successful authenticated logout. The actor ID and username snapshot are taken only from the authenticated user context; failed logins use a null actor and may retain the submitted username as a controlled audit snapshot without resolving it to a user ID. Remote IP uses the direct `RemoteAddr` host only. `X-Forwarded-For`, `X-Real-IP`, and `Forwarded` are ignored until a trusted-proxy model exists. Passwords, session values, and CSRF values are excluded from every authentication audit field.
- 6D.2b audits server create, update, delete, start, stop, restart, and kill actions and port create, update, and delete actions after their API-level result is known. Server and port events carry the authenticated actor, direct remote address, and known resource/server identifiers. Port metadata is restricted to protocol, bind address, and port number; server events never include environment values, executable arguments, or complete request objects. Failure summaries are stable and sanitized rather than raw Runtime, SQL, or host-specific errors. A manual restart produces one `server.restart` event, not additional user-originated stop/start events. Auto-restart system events and permission-denied events are not yet instrumented.
- 6D.2c audits successful and failed file create, edit, rename, move, delete, and upload operations. File audit records contain only sandbox-relative paths and limited metadata such as operation kind, recursive deletion, or upload filename and size. They never contain file text, upload bytes, directory trees, or absolute host paths. Browse, read, download, and other filesystem reads are not audited. Console audit records only processed user input attempts, using the authenticated WebSocket actor, direct connection address, server ID, result, and input byte count. They never contain stdin text, commands, payload previews, console output, connection lifecycle noise, or WebSocket frame content. Console permission denial and unavailable-input failures are locally audited without introducing a global permission-denial framework.
- 6D.2d audits user, group, membership, role, permission-update, and role-assignment mutations. The authenticated caller is always the actor; the affected user, group, or role is the resource. User create and password-reset events exclude passwords, hashes, salts, Argon2 data, sessions, cookies, and token values. Membership events contain at most the affected user ID/username, while assignment events contain subject ID/type and the actual global or server scope. Permission keys may be recorded in a bounded final summary; no catalog, evaluator, or assignment-resolution internals are recorded. Last-active-administrator failures are recorded with a stable business error without changing that protection.
- Consolidated behavior: each successful or relevant failed mutation has one primary API-layer event. Audit persistence errors are logged once and do not retry, recurse, roll back, or replace the original product result. Console Send denials and unavailable input are locally audited; other permission denials are not yet comprehensively audited. Auto-restart system actions are not audited. Audit is not cryptographically tamper-evident and has no retention or export function.
- Audit reads require global-only `Audit.View`; server-scoped Audit.View does not grant access. The read API is backend-authoritative and has no edit, delete, or clear operation. It returns only persisted, bounded audit data without live-resource joins or secret enrichment; SQLite administrators can still alter the database directly.
- Dashboard summaries are capability-filtered server-side: Server, Monitoring, and Ports counts use only servers visible through their respective permissions, and audit recents require global `Audit.View`.
- Application settings are a typed whitelist, not an arbitrary YAML or environment editor. `Settings.View` and `Settings.Manage` are independent global-only platform permissions; server-scoped assignments grant neither. The current API exposes only bounded monitoring interval/history values and requires CSRF for PATCH. It never returns or accepts session/CSRF secrets, password/hash configuration, TLS keys, database paths/credentials, executable paths/arguments, or environment values. Settings updates audit only changed field names. Invalid persisted known values fail safely instead of being silently applied; unknown internal keys are not exposed.
- Diagnostics is read-only and protected by global-only `Settings.View`. It reports only controlled runtime, platform, SQLite migration-health, and monitoring summaries. It does not expose host/database/server paths, environment variables, credentials, network interfaces, process lists, or database contents, and it executes no shell commands.
- Support bundle generation is transport-free and writes only the fixed `manifest.json`, `diagnostics.json`, `settings.json`, `audit-recent.json`, and `servers.json` ZIP entry names; there are no user-controlled names or Zip-Slip paths. It exports sanitized DTOs only: diagnostics, typed safe settings, at most 100 recent audit events, and server summaries. It excludes passwords/hashes, session tokens, cookies, CSRF values, arbitrary environment, executable/argument/working-directory values, SQLite/database files, YAML/configuration, application/server logs, server files/uploads, console input/output, and network or process inventory. Audit unavailability produces a controlled warning rather than a raw error.
- Support downloads require authentication, global-only `Settings.Manage` (with administrator bypass), same-origin validation, and CSRF; `Settings.Manage` does not imply `Settings.View`, and server-scoped assignments grant neither platform permission. The core hard-limits output to 10 MiB; the API completes bounded generation before response commit; no generated bundle is persisted server-side. There is no upload, telemetry, remote-support transmission, encryption, or password-protected ZIP. Its best-effort `support.bundle_generate` audit event is written after generation, so a bundle need not contain its own event. Permission denials are not globally audited in the current architecture.
- Port APIs remain backend-authoritative. `Ports.View` and `Ports.Manage` are independent, server/global-scoped permissions; Manage does not imply View, and PATCH/DELETE enforce the URL server ownership. The registry is authoritative for GameNode-managed ownership. Wildcard IPv4 binds collide with concrete IPv4 binds; IPv6 wildcard handling is conservative. Availability uses temporary TCP/UDP socket binds, never shell commands or hostname resolution. There is no firewall/NAT manipulation or permanent socket reservation. A TOCTOU window remains between this probe and the game process binding its port. A confirmed conflict prevents server start before a Console Session is created.
- Sessions are random opaque cookies, HttpOnly and SameSite=Strict. The database stores only token digests.
- Login and first setup reject cross-origin browser requests. Authenticated mutations additionally require `X-CSRF-Token`.
- Login errors are deliberately generic. API errors do not expose database internals.
- Logging is structured and never includes passwords, session cookies, CSRF tokens, or database credentials.
- Console WebSockets authenticate the session cookie and require `Console.View` before a console subscription is created. They enforce the normal same-origin policy, bound incoming frames, and never log console data or cookie values. `Console.Send` is checked before every input reaches `Session.Input`; a view-only connection stays connected and receives a structured permission-denied event. Console input goes through the ConsoleManager/session validation path, never directly to an OS process.
- Console subscribers use bounded queues. A slow connection is removed by the existing ConsoleManager backpressure policy, so it cannot block process-output capture or other viewers.
- Windows acceptance on 2026-08-11 verified the WebSocket console with two simultaneous subscribers, stdout/stderr replay, live input, and the view-only Send denial. The filesystem harness verified traversal rejection and a real Windows junction escape denial. The test account could not create a symbolic link because it lacked the required Windows privilege; this is a documented platform-test skip, not a relaxation of the Windows reparse-point denial policy.
- Invalid JSON and oversized WebSocket frames are rejected before any console input is written. Disconnecting a client unsubscribes its bounded queue.
- File reads are scoped to each server's configured working directory by `internal/filesystem`. Client paths must be relative; traversal, absolute, drive, and UNC paths are rejected. Canonical root/target checks use path boundaries rather than string prefixes.
- On Linux, symlinks are permitted for reads and writes only when their resolved target stays inside the canonical server root. Delete and rename operate on a final symlink itself rather than its target. On Windows, reparse points (including junctions and symbolic links) beneath a server root are conservatively denied. Special filesystem objects, binary files, and files larger than 4 MiB are not exposed.
- The filesystem API returns generic path errors and does not include absolute host paths in responses or logs. Path-based access has a documented residual OS-level TOCTOU limitation for hostile local writers; no filesystem contents are logged.
- File mutations use the same sandbox as reads. Creates use exclusive creation, edits write and sync a temporary file in the target directory before atomic replacement, moves require both source and destination to remain inside one root, and recursive deletion requires an explicit query parameter. The root itself cannot be mutated.
- Uploads use a bounded `multipart/form-data` request and stream directly into a temporary file within a sandbox-validated existing target directory. Multipart filenames are treated as untrusted filenames, not paths. The default 64 MiB limit is configurable with `filesystem.max_upload_bytes`; incomplete, oversized, and failed uploads do not commit a target file.
- Downloads open only sandbox-validated regular files and stream directly to the HTTP response. Attachment filenames are derived from the validated relative basename and encoded with `Content-Disposition`; absolute host paths, request paths, and file content are not logged.

For production, configure TLS (`server.tls_cert` and `server.tls_key`) so cookies receive the `Secure` attribute. The default HTTP listener is intended for local development only. When TLS is terminated by a local reverse proxy, `server.trust_local_proxy: true` accepts the forwarded scheme and host only when the immediate peer is a loopback address, and also enables secure session cookies. It must not be enabled for a network-reachable proxy.
# Egg import threat model

Egg JSON is untrusted template input. Import is bounded to 256 KiB, 32 nesting levels, 128 variables, 128 compatibility findings, and 16 KiB per relevant string. Variable keys must be process-environment identifiers and are unique case-insensitively. Unknown harmless top-level fields are ignored and reported; malformed documents and important invalid structures receive controlled API errors without parser internals.

GameNode never executes Egg installation scripts, `bash`, `sh`, PowerShell, `cmd`, Docker images, or arbitrary URLs. There is no URL import, image pull, or generic downloader. Recognized SteamCMD shell patterns provide facts to a GameNode-native plan only. The original script is neither persisted nor placed in audit metadata.

Startup remains a direct process boundary. Pipes, redirection, `&&`, `||`, semicolons, background operators, command substitution, backticks, shell builtins/compound commands, unterminated quoting, and absolute executable paths cannot become a launch definition. A direct prefix may be extracted, while all shell content after the first operator is discarded and reported. Placeholder expansion accepts only `{{KNOWN_KEY}}` and `${KNOWN_KEY}` from the template schema; it does not read host environment variables, evaluate strings, or invoke a shell.

Sensitive-variable detection is intentionally conservative and heuristic (`PASSWORD`, `PASS`, `TOKEN`, `SECRET`, `API_KEY`/`APIKEY`, and `AUTH` patterns, case-insensitive). Sensitive source defaults are discarded during normalization. The UI always masks them. Template audit events contain only ID/name, source type, compatibility status, variable count, and installer type—never variable values, raw startup, scripts, Egg JSON, credentials, or paths. Existing diagnostics and support bundles use fixed whitelists and do not query template-variable rows.

`Templates.View` and `Templates.Manage` are independent, global-only permissions. Every template endpoint enforces authorization in the backend; server-scoped assignments never authorize global templates. Mutations require same-origin CSRF validation, and enabled administrators retain the existing bypass.

# Official catalog and NeoForge resolver threat model

Official catalog/template JSON is untrusted network input. Only the compile-time HTTPS GitHub Raw base for the GameNode repository is used; catalog files must be clean relative `.json` paths. Requests have context/client timeouts, 256 KiB limits, status checks, and bounded redirects restricted to the same HTTPS host. Unknown catalog/template schemas and fields, absolute URLs, traversal, unsafe installers, containers, hashes, scripts, and arbitrary launch data fail closed. A malformed entry is isolated; refresh failure preserves last-good cache. v1 intentionally provides no hash or signature infrastructure.

Official templates share the normalized model with imported templates but are read-only and never synchronized into user-editable DB rows. The NeoForge resolver accepts only the known resolver ID, bounded `run.bat`/`run.sh` text, the exact direct Java invocation, and root-relative `user_jvm_args.txt` plus `libraries/net/neoforged/neoforge/<version>/{win,unix}_args.txt`. Absolute paths, traversal, missing files, extra commands, redirection, pipes, shell operators, command substitution, unknown executables, and mismatched platform argfiles fail closed. No launcher is executed and no child process is adopted.

Memory values are bounded integers and `nogui` is boolean; there is no free-form JVM argument field. `user_jvm_args.txt` is required as structural evidence but is not passed to Java, preventing nested argfiles, agents, or classpath injection through that editable file. Java discovery checks `JAVA_HOME/bin` and then `PATH` and never hardcodes a personal installation. EULA acceptance is neither inferred nor written. The existing-directory path is used only by authorized local node operators and is not included in template audit metadata.

# Native SteamCMD provisioning threat model

Provisioning requires independent global `Templates.View` and `Server.Create` capabilities; neither `Templates.Manage` nor a server-scoped assignment implies them. Start, cancel, and registration retry are CSRF-protected mutations. Job reads, cancellation, and retry are limited to the initiating user except for the existing administrator bypass. Registration retry consumes only the bounded persisted normalized snapshot, is serialized per job, and never reruns SteamCMD.

SteamCMD bootstrap uses only compile-time official Valve HTTPS URLs. The downloader applies a timeout, status checks, bounded redirects restricted to the same HTTPS host, and a 128 MiB archive cap. Extraction rejects absolute, drive, UNC, traversal, mixed-separator traversal, symlink/hardlink, special-file, excessive-entry, and excessive-expanded-size inputs. Bootstrap occurs in a sibling temporary directory and is atomically renamed while a manager mutex prevents competing installs.

Official SteamCMD templates can select only the native SteamCMD installer with a positive catalog-owned App ID, anonymous login, `validate`, and the already supported constrained beta branch reference. Unknown installer fields fail JSON decoding. Users cannot submit App IDs or commands. Executables and working directories must be relative, traversal-free paths beneath the server root; shell executables and shell syntax are rejected. Variables substitute within one existing argument element and cannot add arguments. A literal Windows Java classpath separator is accepted only in one relative-path-list argument directly following `-cp`/`-classpath`; it never reaches a shell. Stop behavior is limited to process termination or a single bounded stdin command. A failed install, missing executable, port conflict, or database failure creates no server row; raw output and sensitive values are excluded from API and audit records.

Remote configuration adapters are also untrusted data. References are same-directory JSON basenames beneath the fixed Official source; responses are bounded and cached through the catalog client. A v1 definition can select only compiled `xml-properties`, sectionless `ini-key-values`, or bounded `section-tuple-key-values`, safe relative targets, simple property identifiers, typed fields, restart metadata, and the reviewed initialization/post-start lifecycle. XPath, regex replacement, external URLs, scripts, hooks, arbitrary parsers, and escaping host paths are rejected. The tuple adapter selects exactly one section and container property, preserves unknown tuple properties, and rejects ambiguous duplicate mapped properties; it is not a generic Unreal parser. Optional `seed-from-file` initialization validates and parses a server-root-relative installed source before atomically creating a missing target, and never replaces an existing target with the seed. Symlink-resolved targets must remain inside the server root. INI values cannot contain line breaks and therefore cannot create extra keys. Writes use a private temporary file and previous-file backup. Secret properties are returned only as `configured: true/false`; values and mutation bodies never enter audit metadata. Project Zomboid Lua files are not interpreted or edited.

# Managed launch configuration threat model

Adapter schema v2 adds `managed-launch` adapters whose fields bind to reviewed launch arguments or environment entries instead of a game file. Bindings are a closed compiled whitelist (`launch-value`, `launch-flag`, `launch-secret`, `environment-value`, `environment-secret`). Argument and environment names come only from reviewed Official adapter data; a user supplies a value, never a name. There is no expression language, no index-based argument editing, and no shell. A user value is inserted as exactly one argv element and cannot create an additional argument; NUL and line-break characters are rejected, values are length-bounded, and the resolved argument and environment counts are bounded.

Resolution happens in `internal/gameconfig` and is applied by `servers.Service` immediately before `Runtime.Start`, after port preflight and before any state mutation, console session, or process creation. The resolved launch exists only in memory for that start; it is never persisted, and an incomplete or invalid configuration fails the start closed instead of launching a differently configured game. `servers.Service` remains the lifecycle authority and no second runtime model exists.

Because a managed secret must never enter job state, a provisioning job whose managed configuration contains a secret value writes **no** registration snapshot at all and is reported as not registration-recoverable. Retrying from a redacted snapshot would create a server whose managed secrets are silently missing, so the retry is refused and the operator is told to provision again. A managed configuration without secret values keeps the existing snapshot and retry behavior unchanged.

`launch-secret` and `environment-secret` are the only ways a secret can reach argv or the child environment, and they require a `secret`, `sensitive` field. The existing rule that Official templates may not interpolate sensitive template variables into launch paths or arguments is unchanged. A secret bound this way is stored in `server_config_values`, excluded from the server's persisted arguments and environment, excluded from the persisted provisioning registration snapshot, and never returned by the configuration or server APIs, audit metadata, logs, diagnostics, support bundles, or provisioning job state and events; the API reports only `configured: true/false`. Values remain plaintext in SQLite through the existing persistence model, and application-level at-rest encryption is still a future hardening item.

A game such as Valheim may accept its password only as a process argument. GameNode therefore inserts the secret into the child process argument list at start, where a sufficiently privileged local operating-system user may be able to read it through normal process inspection. That exposure comes from the game's own interface and cannot be removed by GameNode; GameNode does not relax any of its own redaction because of it.

The install command is an executable plus a constructed argument slice. App IDs are positive integers; beta branches use a narrow identifier grammar; authentication is anonymous; beta passwords, credentialed login, Egg flags, and user-supplied commands are rejected. Server targets are names underneath `<data>/servers`, never arbitrary paths. Populated targets and concurrent jobs for one root are rejected. Eggs cannot select a download URL or tool path.

Template values are accepted only for declared editable variables and revalidated by the normalized schema. Expansion substitutes a value into one existing executable/argument field; values cannot add arguments or commands. Sensitive placeholders are forbidden in the executable and masked in returned arguments. The API omits sensitive environment values, audit events contain no values/paths/output, provisioning errors are fixed summaries, and support bundles do not query server environment data. Values remain plaintext in SQLite through the existing environment persistence, and may be visible to privileged local database/process inspection; application-level at-rest secret encryption is a future hardening item.

Installation failure never creates a server record. Database finalization failure can leave an owned target directory, which is reported by `files_may_remain`; GameNode does not recursively delete it automatically. Cancellation kills the installer and prevents subsequent finalization. Restart recovery marks active jobs interrupted and does not claim a resumable transaction.

# Windows console-interrupt stop threat model

`console_interrupt` is a compiled Windows-only stop type, not a free-form signal or stop string. A template declares only the stop type and a bounded timeout (`stop_timeout_seconds`); it can never declare a signal number, a Windows API flag, a control character, a helper executable path, or a stop command — `console_interrupt` with a non-empty `stop_command` fails template validation (`TEMPLATE_UNSUPPORTED_STOP_METHOD`). The choice between `CTRL_C_EVENT` and `CTRL_BREAK_EVENT` is fixed in the reviewed Windows runtime, not configurable data.

Delivery is always scoped to one identity-verified process group, never process group `0`. `Interrupt` re-verifies PID and `StartKey` before sending, exactly like every other lifecycle path, so a reused PID or a stale in-memory instance cannot signal a newer, unrelated process. GameNode never sends `CTRL_C_EVENT` (which can only be broadcast to the entire shared console, group `0`) and instead always sends `CTRL_BREAK_EVENT` addressed to the target's own process group ID; GameNode itself and every sibling server are outside that group and are never signaled. `console_interrupt` requires a matching attached in-memory process instance from the current GameNode process's own lifetime; a rediscovered/detached identity is not given a synthesized console or a forged "safe" interrupt and instead falls back to the existing `terminate` lifecycle for that stop.

Delivery uses no shell, script, or template-defined command. It re-execs the identical, already-trusted GameNode binary as a disposable helper process, dispatched only through an internal environment variable checked before any other `main()` startup (never an argv flag, never documented as a general-purpose CLI mode, never reachable from the HTTP API). The helper is not a second persistent service: it performs exactly one `AttachConsole`/`GenerateConsoleCtrlEvent`/`FreeConsole` sequence and exits, is never a member of the target's process group so it cannot receive the event it delivers, and does not inherit or allocate a visible window (`CREATE_NO_WINDOW`). GameNode's own console attachment is never mutated by this path, so the technique cannot sever GameNode's own ability to receive its own operator-issued Ctrl+C.

Timeout handling is identical to `stdin_command`: on timeout GameNode uses the existing bounded force-kill path, never an unbounded wait, and force-kill usage is logged (never audited with OS error text, handle values, or full arguments) so a controlled outcome remains observable without exposing process internals. `RUNTIME_CONSOLE_INTERRUPT_UNSUPPORTED` and `RUNTIME_CONSOLE_INTERRUPT_FAILED` are the only API/audit-facing codes for this path; they never carry raw Windows error codes, handles, or PIDs. Linux has a stable interface stub that always reports `RUNTIME_CONSOLE_INTERRUPT_UNSUPPORTED` rather than silently no-op succeeding or emulating the concept.

Pelican/Pterodactyl `^C` stop strings from imported Eggs are not automatically normalized to `console_interrupt`; only the reviewed Official Satisfactory template uses it in this milestone. Imported Eggs keep their existing conservative compatibility findings for `^C` until a separate, explicitly reviewed normalization milestone.

# UI theme, sidebar, and wallpaper preferences

Theme, sidebar-collapsed, and wallpaper are personal browser preferences (`web/src/theme.ts`), stored only in the browser's `localStorage` and never sent to the backend. This adds no new HTTP endpoint, no new authentication/CSRF surface, and no new persisted server-side data: `internal/settings`, its authorization, and its audit event are unchanged.

A wallpaper image never leaves the browser. `web/src/wallpaper.ts` accepts only `image/png`, `image/jpeg`, or `image/webp`, decodes the file with `createImageBitmap` (which fails closed on anything that is not real, decodable raster image data regardless of its claimed extension or `Content-Type`), and re-encodes the decoded bitmap through a `<canvas>` before storing it - which rasterizes the image and discards any bytes that are not pixel data. The resulting value is additionally validated against a strict `data:image/(png|jpeg|webp);base64,...` pattern with a bounded length before it is ever written into a CSS custom property, so no remote URL, SVG, inline HTML, or arbitrary CSS/script can reach the DOM through this path. Because the allow-listed pattern only contains base64-alphabet characters, no further escaping is needed to use it safely inside a `style` attribute.

# Remote Node Foundation threat model (v0.5A)

**No default trust.** A GameNode instance never trusts another by IP, hostname, or first contact. Trust begins only when an operator deliberately generates a pairing token on the node being enrolled and supplies it to the enrolling controller out of band.

**Pairing tokens** (`node_pairing_tokens`) are 32 random bytes (base64url), expire after 15 minutes, and are single-use: consuming a token is a transaction that reads-checks-marks-used atomically, and a replayed, expired, or unknown token all fail identically (`ErrPairingTokenInvalid`) so a caller cannot distinguish "already used" from "never existed." Only a SHA-256 hash of the token is stored; the plaintext is returned exactly once, by the generating endpoint's response body, and is never written to a log or audit record.

**Machine credentials** (`node_trusted_callers`) are 32 random bytes issued only after a pairing token is successfully consumed. Only a salted SHA-256 hash is stored (`AuthenticateCaller` uses `crypto/subtle.ConstantTimeCompare`); the plaintext is returned exactly once, in the enrollment response, and is never retrievable again through any API - including the controller's own registry API, whose `publicRemoteNode` projection deliberately omits the stored `Credential` field.

**Human and machine trust are separate domains.** The Node-facing API (`/api/v1/node/info|health|capabilities|enroll`) is authenticated only by `Authorization: Bearer <credential>` checked against `node_trusted_callers`; it performs no same-origin or CSRF check, and a browser session cookie alone never authenticates it (regression-tested). The controller-facing registry API (`/api/v1/remote-nodes*`, `/api/v1/node/pairing-tokens`) is authenticated only by the ordinary browser session, gated by `Node.View`/`Node.Manage`, and requires CSRF like every other mutation - a machine credential never substitutes for a human session there.

**Transport.** `internal/remote.Client` verifies certificates normally (`tls.Config{MinVersion: tls.VersionTLS12}`, no `InsecureSkipVerify`), bounds every request to an 8-second default timeout and every response body to 1 MiB (`io.LimitReader`), and sets `CheckRedirect` to stop at the first response instead of following it - Go's default client would otherwise re-issue the request, `Authorization` header included, against whatever host a compromised or misconfigured remote node's redirect pointed at. There is no per-request arbitrary URL: every method builds its own fixed path against the one endpoint recorded for that enrolled node.

**SSRF.** GameNode does not restrict remote node endpoints to public addresses - an operator legitimately points this at loopback or private-network hosts. The mitigation is narrower: `remote.ValidateEndpoint` normalizes an endpoint to bare `scheme://host[:port]` (rejecting userinfo, path, query, fragment, and non-`http(s)` schemes), the client never accepts a caller-supplied URL for an individual call, and it never forwards a stored credential to a host other than the one that credential was issued for.

**Connection state is presentation-only.** `nodes.Health` (`reachable`/`unreachable`/`authentication_failed`/`protocol_incompatible`/`degraded`/`unknown`) is a UI/audit convenience, never fed into any local authorization or lifecycle decision - "a remote node is unreachable" never implies or triggers any action against that node's own servers, which this controller cannot see or control in v0.5A regardless.

**Audit.** Enrollment, pairing-token issuance, rename, enable/disable, and removal are audited (`audit.NodeEnroll`, `NodePairingTokenCreate`, `NodeUpdate`, `NodeEnable`, `NodeDisable`, `NodeRemove`) with bounded, non-secret metadata (endpoint, node ID, display name, enabled flag - never a token or credential). Routine health-refresh polls, whether from the periodic background loop or a manual "Refresh status" click, are never individually audited.

**Autonomy.** Enrollment never changes what a node can do locally, and never becomes a dependency for it: `cmd/gamenode/main.go`'s heartbeat loop only refreshes registry status, is fully optional, and its failure or a controller's total unavailability never affects any local server's lifecycle.
