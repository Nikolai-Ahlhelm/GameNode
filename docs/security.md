# Security

- Passwords are hashed with Argon2id; plaintext passwords are neither logged nor persisted.
- Local-user creation and password resets reuse the same Argon2id implementation and require passwords of 12–256 characters. There are no composition rules and neither API responses nor logs include password hashes.
- Disabling or deleting a user removes all of that user's sessions immediately; password resets also revoke existing sessions. Disabled and deleted users therefore cannot establish or retain authenticated sessions.
- The last enabled administrator cannot be disabled, deleted, or demoted. Management APIs use global RBAC permissions and normal CSRF protection. `Users.Manage` does not delegate administrator-flag changes; those remain active-admin-only. Login failures remain generic.
- User and group names are restricted to ASCII identifiers and stored under SQLite's case-insensitive uniqueness semantics, avoiding silent Unicode normalization ambiguity.
- RBAC permission keys are selected only from a compiled static catalog; roles and group names have no implicit privilege. The evaluator is allow-only, supports global/server scopes, and denies disabled users before the administrator bypass or assignments. Enabled administrators retain the bypass. Server, Console, Files, and existing Users/Groups/Roles management endpoints consume this evaluator. Platform permissions are checked only at global scope, so server-scoped platform roles cannot expose management data. There is no implicit permission inheritance.
- Sessions are random opaque cookies, HttpOnly and SameSite=Strict. The database stores only token digests.
- Login and first setup reject cross-origin browser requests. Authenticated mutations additionally require `X-CSRF-Token`.
- Login errors are deliberately generic. API errors do not expose database internals.
- Logging is structured and never includes passwords, session cookies, CSRF tokens, or database credentials.
- Console WebSockets authenticate the session cookie and require `Console.View` before a console subscription is created. They enforce the normal same-origin policy, bound incoming frames, and never log console data or cookie values. `Console.Send` is checked before every input reaches `Session.Input`; a view-only connection stays connected and receives a structured permission-denied event. Console input goes through the ConsoleManager/session validation path, never directly to an OS process.
- Console subscribers use bounded queues. A slow connection is removed by the existing ConsoleManager backpressure policy, so it cannot block process-output capture or other viewers.
- Invalid JSON and oversized WebSocket frames are rejected before any console input is written. Disconnecting a client unsubscribes its bounded queue.
- File reads are scoped to each server's configured working directory by `internal/filesystem`. Client paths must be relative; traversal, absolute, drive, and UNC paths are rejected. Canonical root/target checks use path boundaries rather than string prefixes.
- On Linux, symlinks are permitted for reads and writes only when their resolved target stays inside the canonical server root. Delete and rename operate on a final symlink itself rather than its target. On Windows, reparse points (including junctions and symbolic links) beneath a server root are conservatively denied. Special filesystem objects, binary files, and files larger than 4 MiB are not exposed.
- The filesystem API returns generic path errors and does not include absolute host paths in responses or logs. Path-based access has a documented residual OS-level TOCTOU limitation for hostile local writers; no filesystem contents are logged.
- File mutations use the same sandbox as reads. Creates use exclusive creation, edits write and sync a temporary file in the target directory before atomic replacement, moves require both source and destination to remain inside one root, and recursive deletion requires an explicit query parameter. The root itself cannot be mutated.
- Uploads use a bounded `multipart/form-data` request and stream directly into a temporary file within a sandbox-validated existing target directory. Multipart filenames are treated as untrusted filenames, not paths. The default 64 MiB limit is configurable with `filesystem.max_upload_bytes`; incomplete, oversized, and failed uploads do not commit a target file.
- Downloads open only sandbox-validated regular files and stream directly to the HTTP response. Attachment filenames are derived from the validated relative basename and encoded with `Content-Disposition`; absolute host paths, request paths, and file content are not logged.

For production, configure TLS (`server.tls_cert` and `server.tls_key`) so cookies receive the `Secure` attribute. The default HTTP listener is intended for local development only.
