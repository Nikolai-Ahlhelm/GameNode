# Security

- Passwords are hashed with Argon2id; plaintext passwords are neither logged nor persisted.
- Local-user creation and password resets reuse the same Argon2id implementation and require passwords of 12–256 characters. There are no composition rules and neither API responses nor logs include password hashes.
- Disabling or deleting a user removes all of that user's sessions immediately; password resets also revoke existing sessions. Disabled and deleted users therefore cannot establish or retain authenticated sessions.
- The last enabled administrator cannot be disabled, deleted, or demoted. Management APIs use global RBAC permissions and normal CSRF protection. `Users.Manage` does not delegate administrator-flag changes; those remain active-admin-only. Login failures remain generic.
- User and group names are restricted to ASCII identifiers and stored under SQLite's case-insensitive uniqueness semantics, avoiding silent Unicode normalization ambiguity.
- RBAC permission keys are selected only from a compiled static catalog; roles and group names have no implicit privilege. The evaluator is allow-only, supports global/server scopes, and denies disabled users before the administrator bypass or assignments. Enabled administrators retain the bypass. Server, Console, Files, and existing Users/Groups/Roles management endpoints consume this evaluator. Platform permissions are checked only at global scope, so server-scoped platform roles cannot expose management data. There is no implicit permission inheritance.
- Monitoring reads require `Monitoring.View` at the requested server scope. Sampling verifies full process identity before collecting metrics and discards stale samples, so a reused PID is not attributed to a newer process. Sampling errors only degrade health and never interrupt lifecycle or console handling.
- Auto-restart attempts are bounded in a rolling window. Pending generations are cancelled by manual lifecycle intent, and a replacement process receives a fresh identity and console session.
- Audit metadata is server-controlled valid JSON capped at 4096 bytes; it is never automatically copied from request bodies. Audit events never store passwords, hashes, sessions, CSRF tokens, cookies, Authorization headers, console stdin, file contents, or upload contents. The product API exposes no audit PATCH/DELETE. SQLite administrators can still alter the database directly; v0.1 provides neither signatures, hash chains, nor cryptographic tamper evidence. Audit writes are best effort: a persistence error is logged but does not reverse a completed product operation.
- 6D.2a audits normal credential-login success and failure and successful authenticated logout. The actor ID and username snapshot are taken only from the authenticated user context; failed logins use a null actor and may retain the submitted username as a controlled audit snapshot without resolving it to a user ID. Remote IP uses the direct `RemoteAddr` host only. `X-Forwarded-For`, `X-Real-IP`, and `Forwarded` are ignored until a trusted-proxy model exists. Passwords, session values, and CSRF values are excluded from every authentication audit field.
- 6D.2b audits server create, update, delete, start, stop, restart, and kill actions and port create, update, and delete actions after their API-level result is known. Server and port events carry the authenticated actor, direct remote address, and known resource/server identifiers. Port metadata is restricted to protocol, bind address, and port number; server events never include environment values, executable arguments, or complete request objects. Failure summaries are stable and sanitized rather than raw Runtime, SQL, or host-specific errors. A manual restart produces one `server.restart` event, not additional user-originated stop/start events. Auto-restart system events and permission-denied events are not yet instrumented.
- 6D.2c audits successful and failed file create, edit, rename, move, delete, and upload operations. File audit records contain only sandbox-relative paths and limited metadata such as operation kind, recursive deletion, or upload filename and size. They never contain file text, upload bytes, directory trees, or absolute host paths. Browse, read, download, and other filesystem reads are not audited. Console audit records only processed user input attempts, using the authenticated WebSocket actor, direct connection address, server ID, result, and input byte count. They never contain stdin text, commands, payload previews, console output, connection lifecycle noise, or WebSocket frame content. Console permission denial and unavailable-input failures are locally audited without introducing a global permission-denial framework.
- 6D.2d audits user, group, membership, role, permission-update, and role-assignment mutations. The authenticated caller is always the actor; the affected user, group, or role is the resource. User create and password-reset events exclude passwords, hashes, salts, Argon2 data, sessions, cookies, and token values. Membership events contain at most the affected user ID/username, while assignment events contain subject ID/type and the actual global or server scope. Permission keys may be recorded in a bounded final summary; no catalog, evaluator, or assignment-resolution internals are recorded. Last-active-administrator failures are recorded with a stable business error without changing that protection.
- Consolidated behavior: each successful or relevant failed mutation has one primary API-layer event. Audit persistence errors are logged once and do not retry, recurse, roll back, or replace the original product result. Console Send denials and unavailable input are locally audited; other permission denials are not yet comprehensively audited. Auto-restart system actions are not audited. Audit is not cryptographically tamper-evident and has no retention or export function.
- Audit reads require global-only `Audit.View`; server-scoped Audit.View does not grant access. The read API is backend-authoritative and has no edit, delete, or clear operation. It returns only persisted, bounded audit data without live-resource joins or secret enrichment; SQLite administrators can still alter the database directly.
- Dashboard summaries are capability-filtered server-side: Server, Monitoring, and Ports counts use only servers visible through their respective permissions, and audit recents require global `Audit.View`.
- Application settings are a typed whitelist, not an arbitrary YAML or environment editor. `Settings.View` and `Settings.Manage` are independent global-only platform permissions; server-scoped assignments grant neither. The current API exposes only bounded monitoring interval/history values and requires CSRF for PATCH. It never returns or accepts session/CSRF secrets, password/hash configuration, TLS keys, database paths/credentials, executable paths/arguments, or environment values. Settings updates audit only changed field names. Invalid persisted known values fail safely instead of being silently applied; unknown internal keys are not exposed.
- Diagnostics is read-only and protected by global-only `Settings.View`. It reports only controlled runtime, platform, SQLite migration-health, and monitoring summaries. It does not expose host/database/server paths, environment variables, credentials, network interfaces, process lists, or database contents, and it executes no shell commands.
- Support bundle generation is transport-free and writes only the fixed `manifest.json`, `diagnostics.json`, `settings.json`, `audit-recent.json`, and `servers.json` ZIP entry names; there are no user-controlled names or Zip-Slip paths. It exports sanitized DTOs only: diagnostics, typed safe settings, at most 100 recent audit events, and server summaries. It excludes passwords/hashes, session tokens, cookies, CSRF values, arbitrary environment, executable/argument/working-directory values, SQLite/database files, YAML/configuration, application/server logs, server files/uploads, console input/output, and network or process inventory. Audit unavailability produces a controlled warning rather than a raw error.
- Support downloads require authentication, global-only `Settings.Manage` (with administrator bypass), same-origin validation, and CSRF; `Settings.Manage` does not imply `Settings.View`, and server-scoped assignments grant neither platform permission. The core hard-limits output to 10 MiB; the API completes bounded generation before response commit; no generated bundle is persisted server-side. There is no upload, telemetry, remote-support transmission, encryption, or password-protected ZIP. Its best-effort `support.bundle_generate` audit event is written after generation, so a bundle need not contain its own event. Permission denials are not globally audited in the current architecture.
- Port APIs remain backend-authoritative. `Ports.View` and `Ports.Manage` are independent, server/global-scoped permissions; Manage does not imply View, and PATCH/DELETE enforce the URL server ownership. The registry is authoritative for GameNode-managed ownership. Wildcard IPv4 binds collide with concrete IPv4 binds; IPv6 wildcard handling is conservative. Availability uses temporary TCP/UDP socket binds, never shell commands or hostname resolution. There is no firewall/NAT manipulation or permanent socket reservation. A TOCTOU window remains between this probe and the game process binding its port. A confirmed conflict prevents server start before a Console Session is created.
- Sessions are random opaque cookies, HttpOnly and SameSite=Strict. The database stores only token digests.
- Login and first setup reject cross-origin browser requests. Authenticated mutations additionally require `X-CSRF-Token`.
- Login errors are deliberately generic. API errors do not expose database internals.
- Logging is structured and never includes passwords, session cookies, CSRF tokens, or database credentials.
- Console WebSockets authenticate the session cookie and require `Console.View` before a console subscription is created. They enforce the normal same-origin policy, bound incoming frames, and never log console data or cookie values. `Console.Send` is checked before every input reaches `Session.Input`; a view-only connection stays connected and receives a structured permission-denied event. Console input goes through the ConsoleManager/session validation path, never directly to an OS process.
- Console subscribers use bounded queues. A slow connection is removed by the existing ConsoleManager backpressure policy, so it cannot block process-output capture or other viewers.
- Windows acceptance on 2026-08-11 verified the WebSocket console with two simultaneous subscribers, stdout/stderr replay, live input, and the view-only Send denial. The filesystem harness verified traversal rejection and a real Windows junction escape denial. The test account could not create a symbolic link because it lacked the required Windows privilege; this is a documented platform-test skip, not a relaxation of the Windows reparse-point denial policy.
- Invalid JSON and oversized WebSocket frames are rejected before any console input is written. Disconnecting a client unsubscribes its bounded queue.
- File reads are scoped to each server's configured working directory by `internal/filesystem`. Client paths must be relative; traversal, absolute, drive, and UNC paths are rejected. Canonical root/target checks use path boundaries rather than string prefixes.
- On Linux, symlinks are permitted for reads and writes only when their resolved target stays inside the canonical server root. Delete and rename operate on a final symlink itself rather than its target. On Windows, reparse points (including junctions and symbolic links) beneath a server root are conservatively denied. Special filesystem objects, binary files, and files larger than 4 MiB are not exposed.
- The filesystem API returns generic path errors and does not include absolute host paths in responses or logs. Path-based access has a documented residual OS-level TOCTOU limitation for hostile local writers; no filesystem contents are logged.
- File mutations use the same sandbox as reads. Creates use exclusive creation, edits write and sync a temporary file in the target directory before atomic replacement, moves require both source and destination to remain inside one root, and recursive deletion requires an explicit query parameter. The root itself cannot be mutated.
- Uploads use a bounded `multipart/form-data` request and stream directly into a temporary file within a sandbox-validated existing target directory. Multipart filenames are treated as untrusted filenames, not paths. The default 64 MiB limit is configurable with `filesystem.max_upload_bytes`; incomplete, oversized, and failed uploads do not commit a target file.
- Downloads open only sandbox-validated regular files and stream directly to the HTTP response. Attachment filenames are derived from the validated relative basename and encoded with `Content-Disposition`; absolute host paths, request paths, and file content are not logged.

For production, configure TLS (`server.tls_cert` and `server.tls_key`) so cookies receive the `Secure` attribute. The default HTTP listener is intended for local development only.
# Egg import threat model

Egg JSON is untrusted template input. Import is bounded to 256 KiB, 32 nesting levels, 128 variables, 128 compatibility findings, and 16 KiB per relevant string. Variable keys must be process-environment identifiers and are unique case-insensitively. Unknown harmless top-level fields are ignored and reported; malformed documents and important invalid structures receive controlled API errors without parser internals.

GameNode never executes Egg installation scripts, `bash`, `sh`, PowerShell, `cmd`, Docker images, or arbitrary URLs. There is no URL import, remote repository sync, image pull, or generic downloader. Recognized SteamCMD shell patterns provide facts to a GameNode-native plan only. The original script is neither persisted nor placed in audit metadata.

Startup remains a direct process boundary. Pipes, redirection, `&&`, `||`, semicolons, background operators, command substitution, backticks, shell builtins/compound commands, unterminated quoting, and absolute executable paths cannot become a launch definition. A direct prefix may be extracted, while all shell content after the first operator is discarded and reported. Placeholder expansion accepts only `{{KNOWN_KEY}}` and `${KNOWN_KEY}` from the template schema; it does not read host environment variables, evaluate strings, or invoke a shell.

Sensitive-variable detection is intentionally conservative and heuristic (`PASSWORD`, `PASS`, `TOKEN`, `SECRET`, `API_KEY`/`APIKEY`, and `AUTH` patterns, case-insensitive). Sensitive source defaults are discarded during normalization. The UI always masks them. Template audit events contain only ID/name, source type, compatibility status, variable count, and installer type—never variable values, raw startup, scripts, Egg JSON, credentials, or paths. Existing diagnostics and support bundles use fixed whitelists and do not query template-variable rows.

`Templates.View` and `Templates.Manage` are independent, global-only permissions. Every template endpoint enforces authorization in the backend; server-scoped assignments never authorize global templates. Mutations require same-origin CSRF validation, and enabled administrators retain the existing bypass.

# Native SteamCMD provisioning threat model

Provisioning requires independent global `Templates.View` and `Server.Create` capabilities; neither `Templates.Manage` nor a server-scoped assignment implies them. Start and cancel are CSRF-protected mutations. Job reads/cancellation are limited to the initiating user except for the existing administrator bypass.

SteamCMD bootstrap uses only compile-time official Valve HTTPS URLs. The downloader applies a timeout, status checks, bounded redirects restricted to the same HTTPS host, and a 128 MiB archive cap. Extraction rejects absolute, drive, UNC, traversal, mixed-separator traversal, symlink/hardlink, special-file, excessive-entry, and excessive-expanded-size inputs. Bootstrap occurs in a sibling temporary directory and is atomically renamed while a manager mutex prevents competing installs.

The install command is an executable plus a constructed argument slice. App IDs are positive integers; beta branches use a narrow identifier grammar; authentication is anonymous; beta passwords, credentialed login, Egg flags, and user-supplied commands are rejected. Server targets are names underneath `<data>/servers`, never arbitrary paths. Populated targets and concurrent jobs for one root are rejected. Eggs cannot select a download URL or tool path.

Template values are accepted only for declared editable variables and revalidated by the normalized schema. Expansion substitutes a value into one existing executable/argument field; values cannot add arguments or commands. Sensitive placeholders are forbidden in the executable and masked in returned arguments. The API omits sensitive environment values, audit events contain no values/paths/output, provisioning errors are fixed summaries, and support bundles do not query server environment data. Values remain plaintext in SQLite through the existing environment persistence, and may be visible to privileged local database/process inspection; application-level at-rest secret encryption is a future hardening item.

Installation failure never creates a server record. Database finalization failure can leave an owned target directory, which is reported by `files_may_remain`; GameNode does not recursively delete it automatically. Cancellation kills the installer and prevents subsequent finalization. Restart recovery marks active jobs interrupted and does not claim a resumable transaction.
